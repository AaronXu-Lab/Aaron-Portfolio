> AI 可以参与发现和优化流程，但当流程进入稳定执行阶段，它得让人看得见、查得动。

## 一、开放探索的矛盾

### 1. 设计需要不确定性，但不需要无限的不确定性

我是个设计师，设计的工作流经常从一个模糊的问题开始。早期阶段你得同时想产品方向和用户需求，这个过程本身就是开放的，也必须允许试错。说白了，设计师是这样一种生物：会刻意避开大路走，转而去找有趣小路，甚至自己开辟道路，在开路的过程中总结经验，并以此为乐。

这似乎非常适合交给 AI。AI 能快速生成大量方案，也能沿着不同方向一直展开下去。

但是，always have a but。当设计师本身还在发散，而 AI 又在每一个方向上继续发散时，问题很快就会失去边界。你原本只想验证一个方向，它顺手把信息结构和产品定位一起改了；最后得到的东西看起来很多，却难以判断每个方案到底在回答什么问题。创意就这么"失控"了，人的意图在多轮无效生成里被稀释掉，到后面甚至忘了最开始要解决的是什么。

### 2. AI Slop 是个立场问题

更严重的问题是 AI Slop。

当 AI 缺少明确方向时，它会选最常见、最安全的那个方案。在界面设计里，这表现为过度圆角的卡片，和那种看似精致、但没有明确产品判断的布局。这些东西通常不能算错，第一眼看上去甚至还不错，但它们很难体现具体业务和具体用户之间的差异。所谓"AI 感"，就是 AI 在缺少判断标准时 fallback 到统计意义上的通解，而这种平均化会把设计里最要紧的取舍和立场一点点磨平。

所以顺序得反过来：人先挑出值得探索的方向，AI 在这个方向内往下延展，人再判断哪些延展值得留。路是人挑的，AI 只管在这条路上多跑几步。

## 二、Agent 确实解决了真问题

传统工作流要求人在执行前先定义好步骤：先做什么，再做什么，遇到什么条件进哪个分支。这种方式适合结构稳定、规则明确的任务。但设计、研究、产品规划这类工作，往往从一开始就带着不确定性，很多时候人甚至不知道正确的流程应该长什么样。

Agent 的价值就在这里。它会根据上下文调整计划，信息不够就自己去找材料，目标太模糊就先拆成子任务，执行到一半还可能翻出你原先没想到的问题。

几个它特别擅长的场景：需求往往只是表象，让 Agent 去梳理目标和约束，一句模糊的描述才慢慢变得能讨论；流程还没成形时，它能摆出几条不同的执行路径，陪你比成本、比风险；人受限于已有经验，它能从别的角度补上被忽略的边界情况。长尾情况多到穷举不完的时候，它就是规则之外的那层弹性。

于是问题变成了：**Agent 应该在流程的哪个阶段拥有多大的自主权？**

## 三、每次重新规划，代价在哪

既然 Agent 能规划任务，为什么不让它每次执行都重新想一遍？一次性的开放任务里，这么做没问题。但要持续运行、反复交付、进真实业务环境，每次重新规划就意味着流程本身一直在变。

同样的输入，不同的时间，Agent 会选不同的路。探索阶段这不算事，可到了稳定执行阶段，团队连几个最基本的问题都答不上来：这次跟上次比，哪一步变了？结果变好是策略有效，还是碰巧？路径不可预测，人就没法积累对系统的认识。

而且你也看不见它是怎么走的。完全自主规划的 Agent 只给目标和最终结果，就算系统留了中间的思考和工具调用记录，那些记录也很难拼成一个能对比的流程结构。传统工作流把关键步骤摆在明面上：输入是什么，经过哪些处理，什么地方要人工确认。

真正的代价在出问题的那天。固定工作流失败了，你一个节点一个节点查输入输出就行；Agent 每次都重新规划的话，失败的来源可能是计划本身，也可能是工具选择或者执行顺序。除了"这一步为什么错了"，你还得回答"这一次为什么产生了这些步骤"。

调试成本一下就上去了。

## 四、个人要可控，组织要稳定

可控不等于每一步都得人手动点一遍。真正的可控是人清楚地知道：哪些步骤固定，哪些允许 AI 自己判断；什么情况下它必须停下来问一句；出了异常退回到哪里。边界划出来，AI 的能力才算真的嵌进了工作里。

光有结果还不够。重复任务里，人还得判断结果可不可信，出问题时得快速找到原因。可视化工作流的核心价值就在这儿：每个节点都是观察点，输入输出摆在那儿等着被验证。出了事，你至少知道该去看哪一格。

个人能容忍偶然的变化，组织不能。一个流程一旦牵扯到客户、财务或者跨部门协同，出错就得有人担责，这时候稳定压倒效率。组织需要知道流程正常时怎么跑，异常时怎么停，以及谁有权改它。这么看，传统工作流反而比 Agent 更适合组织。

规模再大一点，问题会更明显。个人项目里一个人能同时握住目标、数据和执行方式，但组织的流程通常横跨好几个角色和系统：数据清洗、模型调用、人工审批、写回外部系统，没有谁能长期掌握全部细节。流程必须变成一个大家都读得懂、也都能维护的东西。

Agentic Workflow 目前还没解决这件事。流程主要活在 Agent 的动态规划里，别人在执行前看不到完整结构，也没法针对某个稳定步骤展开讨论。团队成员看到了目标、提示词、某次运行记录，却仍然确认不了下一次会不会一样跑。协作就退化成了"共同操作黑箱"，出了事谁也负不了责。传统工作流提供的协作界面清楚得多：产品在上面讨论业务逻辑，工程在上面检查系统依赖。不然大家开会时，说的到底是不是同一个东西？

流程被显式表达出来，才进得了版本管理和权限控制，也才谈得上复制和交接。人来人往，经验不会跟着谁一起走掉。Agent 提高的是个人能力的上限，Workflow 决定这种能力能不能进组织。

## 五、融合

Agentic Workflow 和传统 Workflow 从来不冲突。让 Agent 参与流程的发现和优化，把验证过的部分沉淀成显式工作流，再在固定流程内部留几个需要判断的 Agent 节点，处理规则穷举不完的情况。

大概分三层。最开始，人给出业务目标和不能碰的红线，Agent 帮着补信息、拆问题、提路径，这一步就该充分探索，因为它的任务本来就是发现流程。等某些步骤反复被证明有效，就别再让 Agent 每次重新发明了，把它们变成显式的节点和条件，能测试，也方便别人接手维护。剩下那些不适合固定的，比如理解开放文本、根据上下文选策略，继续交给 Agent，只要自主性关在合理范围里。

所以一个成熟的 AI 工作流里，确定性的规则节点和有限自主权的 Agent 节点是并存的，中间还得插上必要的人工确认。取彼之长，避己之短。

## 六、为什么"Difys"仍然重要

> 这里的 Dify 泛指以它为代表的可视化 AI 工作流工具，不限于 Dify 平台本身。

Agent 概念火起来之后，可视化 Workflow 很容易被当成一种过渡形态：模型都能自主规划了，还要人手动连节点干嘛？

但会做和扛得住是两回事。Dify 这类平台的价值，恰恰是让团队自己决定哪里需要确定性，哪里必须有人工介入。它跟 Agent 根本不在一条赛道上。Agent 越强，越需要一个结构来接住它，否则模型能力涨多少，不可预测性和协作成本就跟着涨多少。

Workflow 干的事其实很土：把你已经想明白的判断存下来，下次别再想一遍。所以 Difys 仍然重要。让 Agent 帮我们发现和改进流程，但别让它每次执行都重新发明一遍。
